# ADR 0004 — Measurement rig: one harness, five targets, honest drivers

Date: 2026-10-12 · Status: accepted · Piece: E1-002 · Plan: D7, D9, §5, §6, §7, R1, R8

## Context

Every later piece is judged by comparing our document with the native contenteditable of the same browser (B1) and with the ProseMirror basic example (B2), on Chromium, Firefox and WebKit (desktop), Safari on the iOS simulator "Ether iPhone 17 Pro" and Chrome on the Android emulator "ether". The instrument has to exist and be trustworthy before the engine does: it must not report a pass for something it could not do, and it must catch a planted bug.

## Decision

- **One recorder, three subjects.** `bench/oracle/recorder.js` (classic script, no dependencies) is loaded by the oracle and the stub and injected into the ProseMirror page and our document through the driver's evaluate. It resets the starting content, places selections (block/offset or DOM path), computes pointer coordinates and records after every step: blocks (type, text, mark digits in the format-v0 encoding), selection as [block, offset], `beforeinput`/`input`/composition/clipboard/drag events, page errors; for ProseMirror also the document JSON, undo depth and stored marks (read through `window.view` and `window.PM`, no ProseMirror code copied); for our document the `window.webdoc` API values and the ghost.
- **Drivers.** Playwright (headless) for the desktop engines; for iOS, Safari on the simulator in normal mode, with scripts evaluated over the simulator's Web Inspector socket (`test/rig/drivers/wir.mjs`: binary property lists over the `webinspectord_sim` unix socket of the Ether simulator's `launchd_sim`, JSON protocol through `Target.sendMessageToTarget`) and taps and typing through an XCUITest runner (`test/rig/ios-typer`, one long-running UI test fed command files, built with `xcodebuild` into `test-results/`); the W3C WebDriver client against `safaridriver` (`platformName: "iOS"`, `safari:useSimulator`, `safari:deviceName`) stays available as `ETHER_IOS_DRIVER=webdriver`; Playwright `connectOverCDP` through `adb forward … localabstract:chrome_devtools_remote` for Android, with `adb reverse` for the test server. Composition uses CDP `Input.imeSetComposition` + `Input.insertText` (chromium, android-chrome); paste uses the browser clipboard API plus Mod+V (headless clipboards, the macOS pasteboard is untouched — checked with `pbpaste`) On iOS paste is unsupported-by-driver (Cmd+V needs a modifier, see below).
- **A driver limitation is never a pass.** Steps outside a driver's capabilities are `unsupported-by-driver`; the scenario and the target become `incomplete`, which the gates report as not-checked. Silent no-ops are detected: a keyboard probe types "ab" before every suite and disables keyboard steps when the text does not arrive; a drag that fires no `dragstart` is unsupported; a driver that delivers only some keys declares them (`page.canKey`), every other key step is unsupported. Coverage of the Phase-1 inputType matrix is reported as observed events per target, not as intent.
- **Determinism is checked, not assumed.** The fuzz generator (mulberry32, weighted alphabet of §5, 50–200 steps) is a self-contained function; the rig evaluates its source in every browser and compares the SHA-256 of each action list with Node's, and each report carries the digest over all seeds. The planted-bug suite runs native against native over the same seeds as a control.
- **Planted bug.** `bench/stubs/broken.html` is the oracle plus one bug (Backspace drops every "ü" of the caret's text node). The fuzzer runs stub against native (I4, text + caret per step) until the first divergence, shrinks the failing prefix with ddmin over steps and then over graphemes, and saves the minimal scenario in `test/scenarios/regressions/`. Every corpus run replays these regressions against the stub (planted control): a rig that stops seeing the bug turns G4/G6 red.
- **Invariants I1–I8** are pure functions over snapshots (`test/rig/invariants.mjs`, documented in `test/README.md`) with `pass`/`fail`/`inactive`; inactive while `window.webdoc` lacks the needed API, never counted as pass. I3, I4 and I8 reuse `src/ledger.js` and `src/model.js` in Node.
- **Devices.** `tools/devices.mjs` touches only "Ether iPhone 17 Pro" (iOS 26.5) and AVD "ether" (android-36 google_apis arm64-v8a, pixel_6, console port 5580), proves every other simulator/AVD/emulator unchanged before and after, and runs every `simctl`/`adb`/`emulator`/`avdmanager` call through `timed()`; the emulator daemon runs under a boot watchdog. A unit test greps `tools/` and `test/` for device calls outside `timed()`.
- **ProseMirror version.** The example bundle contains no version string. The rig records the bundle's URL, size, SHA-256, `Last-Modified` and `ETag`, and infers prosemirror-view as the newest npm release published before `Last-Modified` (method stated in every report).
- **Gates.** G4 runs the corpus on the desktop targets (native for every scenario, ProseMirror for structural/marks/history scenarios, our four dist variants over http and `file://`, planted control); G6 does the same on the mobile targets plus the fuzz on our document; G5 fuzzes our document on desktop. Fuzz on our document stays inactive (not-checked) until it has an editing surface.

## Findings on this machine (2026-10-12)

- Composition automation exists only through CDP (chromium, android-chrome), as expected (R1).
- Native drag and drop of a selection is reachable with Playwright on Firefox only; Chromium and WebKit fire no `dragstart` for a mouse drag (new and old headless Chromium tried).
- Playwright's WebKit uses its macOS key-binding table: Shift+Enter gives `insertParagraph`, Meta+B/Meta+I are not bound (Safari binds them through the Format menu).
- Android Chrome drops the first key events after a script focus until its input connection exists; the runner waits 500 ms after each reset. Only the front tab receives keys and clipboard access; the runner brings the active tab to the front and waits for `document.hasFocus()`.
- **iOS simulator: no text input through `safaridriver`.** A WebDriver session puts Safari into automation mode. Its key input — Perform Actions and Element Send Keys alike — reaches the page only as `keydown`/`keypress`/`keyup`; no text is inserted into any editing host, not even a `<textarea>`. A W3C touch tap focuses the element in the DOM but starts no input session (no caret, no software keyboard; the key window's first responder stays Safari's `BrowserController`, per the simulator log). Real input is blocked too: an XCUITest tap and `typeText` into Safari while a WebDriver session is open change nothing, and neither does a WebDriver focus after XCUITest typing. Without a WebDriver session the same XCUITest tap shows the keyboard and `typeText("ab")` arrives as `keydown` + `beforeinput insertText` + `input`. Hence the iOS driver above: the inspector connection does not switch Safari into automation mode.
- **iOS keys with the software keyboard.** The Simulator's global preference `ConnectHardwareKeyboard` is 0 (read, not changed). In that state XCUITest `typeText` delivers text (including "ü"), Backspace (`"\b"` → `deleteContentBackward`) and Enter (`"\n"` → `insertParagraph`); `typeKey` delivers plain arrows. Measured no-ops: `typeKey` with a modifier drops the modifier (Shift+ArrowLeft moves the caret), `typeKey` Backspace/Enter/Delete and Command+A/B/V/Z deliver nothing, forward Delete via `typeText` gives `keydown` without an edit. These steps are unsupported-by-driver on `ios-safari`. Whether a connected hardware keyboard makes them work is not verified: the preference is global for the Simulator app and changing it is Joel's decision.
- A tap into ProseMirror's editor froze Safari's automation under `safaridriver` (the page jumped to its end, every further command timed out); that driver keeps its recovery (deadline per command, `simctl terminate` of Safari on the Ether simulator only, new session). The default iOS driver quits Safari on the Ether simulator once at start, so a Safari left in automation mode by an earlier session cannot block input.

## Consequences

- With the drivers above, no target can run the whole corpus: composition is missing on Firefox, WebKit and iOS; drag on Chromium, WebKit and both mobile targets; keys with modifiers, forward Delete, shortcuts, undo/redo and paste on iOS. G4 and G6 therefore report not-checked even when every executed step is fine. Turning a documented driver ceiling into an accepted exception is Joel's decision (PHASE-1.md §6: only Joel relaxes a gate).
- Later pieces get their evidence from the same reports: per-step snapshots of B1 and B2, the observed inputType coverage, and I1–I8 as soon as `window.webdoc` grows.
- The ProseMirror runs need network access to prosemirror.net; a network failure is a red G4/G6, not a silent skip.

## Alternatives considered

- **Playwright `_android`** — needs the chrome://flags switch "Enable command line on non-rooted devices"; `connectOverCDP` through `adb forward` works on the userdebug image without touching Chrome settings (dossier platform.md §4).
- **`document.execCommand('insertText')` on iOS** — rejected: it would measure a script API, not native typing.
- **`safaridriver` for iOS** — kept as `ETHER_IOS_DRIVER=webdriver`, but not the default: in automation mode no text reaches the page (findings above).
- **Changing the Simulator's `ConnectHardwareKeyboard`** — not done: it is a global preference of the Simulator app used by Joel's other simulators; it may unlock modifiers on iOS and is Joel's decision. IME composition on iOS stays with E1-009 (simulator keyboard scripts) and X-04 (manual checklist).
- **Typing via the macOS pasteboard** — rejected: it would overwrite the owner's clipboard.
